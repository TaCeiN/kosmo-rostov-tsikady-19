# Промт: веб-интерфейс NDVI-анализа полей (продуктовый MVP)

> Это техническое задание для исполнителя (человека или ИИ-агента), который
> пишет фронтенд поверх готового бэкенда в этой же папке. ML трогать не нужно:
> модель обучена, метрики посчитаны, API работает.

---

## 0. Как этим документом пользоваться

Порядок чтения при старте работы, ровно такой:

1. Этот файл целиком.
2. `API.md` — контракт HTTP.
3. `openapi.json` — машинное описание, **источник типов**. Сгенерируй из него
   TypeScript-типы (`openapi-typescript`), не переписывай руками.
4. `samples/analyze_response.json` — живой ответ бэкенда, 0.9 МБ. На нём
   проверяется весь экран разбора без запущенного бэкенда и без Earth Engine.
5. `data/meta.json` + любой `data/series/AOI-0001.json` — форма статических
   данных для демо-режима.

Раздел «§13. Грабли» — не рекомендации, а требования. Каждая позиция там уже
стоила кому-то времени.

## 1. Что за продукт

Спутники (Sentinel-2, Landsat, MODIS) снимают сельхозполя. Из снимков считается
**NDVI** — индекс зелёности растительности, от −0.2 до 1.0. Ряд дырявый:
облачность выбивает до 70% суток.

Обученная модель (LightGBM, 106 признаков):
1. **восстанавливает** пропущенные сутки — получается сплошной суточный ряд;
2. по восстановленному ряду **находит периоды угнетения вегетации** и
   **объясняет их погодой** (осадки и температура за 30 дней против нормы).

Качество на скрытых ответах организаторов: **RMSE 0.064, R² 0.913, 74.4%
предсказаний в пределах ±0.05**. Линейная интерполяция для сравнения: RMSE
0.097, 52.5% в ±0.05. То есть модель бьёт наивный бейзлайн в полтора раза.

**Пользователь** — агроном или аналитик агрохолдинга. Он хочет обвести своё поле
на карте и получить ответ на вопрос «что с ним было в такие-то годы и почему».
Он не знает, что такое z-score, и не должен узнать: интерфейс обязан переводить
статистику в человеческий язык.

**Регион** — только Ростовская область (рамка `region_box` из `GET /meta`).
Модель обучена на ней; за её пределами климатнорма и культуры другие, и ответ
будет уверенной чепухой. Это ограничение продукта, а не баг.

## 2. Стек — зафиксирован, не выбирать заново

| слой | решение | почему именно так |

| данные/сеть | **TanStack Query v5** | поллинг задачи, ретраи, кэш, отмена — всё штатное |
| состояние UI | **Zustand** | выбранный полигон, годы, культура, режим |
| типы API | **openapi-typescript** из `openapi.json` | ручные типы разъедутся с бэкендом |
| CSV | **PapaParse** (worker: true) | для экрана `/predict` |
| роутинг | **react-router 6** | 4 экрана |
| стили | **Tailwind CSS** + свои токены | быстро и без спора о дизайн-системе |
| тесты | **Vitest** + **@testing-library/react**; для e2e — **Playwright** (опционально) | см. §12 |

`node >= 20`, пакетный менеджер — `pnpm` (сгодится и npm).

## 4. Контракт бэкенда — что реально нужно знать

Пять эндпоинтов. Полностью — в `API.md`, здесь только то, что диктует UI.

### `GET /health`
```json
{"status":"ok","features":106,"config":{"target":"raw","clip":[-0.2,1.0],"rounds":40,"seed":0,"n_features":106}}
```
Дёргать **на старте приложения**, чтобы отличить «бэкенд не поднят» от «запрос
упал». Первый вызов грузит модель с диска — пара секунд, это нормально.

### `GET /meta` — по нему строится вся форма запроса
```json
{"region_box":{"min_lon":38.3,"min_lat":46.8,"max_lon":41.3,"max_lat":49.3},
 "crop_types":["озимая пшеница","зерновые","подсолнечник","пастбища/зерновые","неизвестно"],
 "years":{"min":2010,"max":2025,"default":[2016,2025],"min_span":3},
 "max_area_ha":5000.0,
 "gee_available":true,
 "typical_fetch_seconds":60}
```
**Ничего из этого не хардкодить.** Границы карты, список культур, границы
слайдера лет, лимит площади, текст ошибок — всё оттуда.
`gee_available: false` → карту прячем, показываем демо-режим (§8).

> Не путать с `data/meta.json`. Совпадение имён случайное:
> `GET /meta` — про лимиты сервиса, `data/meta.json` — про 78 готовых полигонов.

### `POST /analyze` → задача
Запрос:
```json
{"geometry":{"type":"Polygon","coordinates":[[[39.8408,48.0056],[39.8441,48.0056],[39.8441,48.0079],[39.8408,48.0079],[39.8408,48.0056]]]},
 "years":[2016,2025],
 "crop_type":"озимая пшеница"}
```
- `geometry` — GeoJSON `Polygon` / `MultiPolygon` в WGS84. `Feature` тоже
  принимается: Leaflet.draw отдаёт именно его, разворачивать не обязательно.
- `years` — `[первый, последний]` разворачивается бэкендом в диапазон; можно и
  полным списком. **Минимум 3 сезона.**
- `crop_type` — из `/meta`, необязательно, но с ним точность выше.

Ответ (мгновенно):
```json
{"job_id":"eb86dfe8354743999abdf2633d3289a8","status":"queued","area_ha":6.2,
 "years":[2016,…,2025],"poll":"/analyze/eb86dfe8354743999abdf2633d3289a8","expected_seconds":80}
```
`expected_seconds` = `40 + 4 × число_лет` — используй его для прогресс-бара, не
выдумывай своё.

Отказы — **все до постановки задачи, мгновенные**:

| код | когда | что показать |
|---|---|---|
| 400 | geometry не Polygon/MultiPolygon | «нужен GeoJSON Polygon или MultiPolygon» |
| 400 | меньше 3 сезонов | объяснение про leave-one-year-out |
| 400 | площадь > `max_area_ha` | «обведи поле, а не район» + фактическая площадь |
| 400 | вне `region_box` | «за его пределами другие культуры и другая климатнорма» |
| 503 | Earth Engine не настроен | инструкция + кнопка «Перейти в демо-режим» |

**Все четыре 400 обязаны быть проверены на фронте до отправки.** Пользователь
не должен узнавать о лимите площади после того, как обвёл полрайона. FastAPI
кладёт текст в поле `detail` — показывай его, он написан по-русски и по делу.
422 (тело не по схеме) — это баг фронта, показывать техтекст не надо, но в
консоль залогировать.

### `GET /analyze/{job_id}` — поллинг раз в 2500 мс
```jsonc
// queued
{"status":"queued","stage":"в очереди","progress":0.0,"created":1757000000.0,"area_ha":6.2,"years":[…]}
// running, стадия 1
{"status":"running","stage":"тянем спутники и погоду","progress":0.1, …}
// running, стадия 2 — появляется fetch, ПОКАЗАТЬ СРАЗУ
{"status":"running","stage":"считаем признаки и восстанавливаем ряд","progress":0.7,
 "fetch":{"days":2130,"observed":728,"coverage_%":34.2,
          "by_sensor":{"S2":396,"Landsat":335,"MODIS":130},
          "weather_filled_%":100.0,"years":[…]}}
// done
{"status":"done","stage":"готово","progress":1.0,"result":{…}}
// error
{"status":"error","progress":1.0,"error":"за выбранной областью нет ни одного наблюдения. Обычно это вода, город или область вне покрытия — выбери пашню."}
```
`status ∈ queued | running | done | error`. Текст `error` — человеческий,
показывай как есть.

**404 = задача потеряна** (истёк час хранения или бэкенд перезапускался).
Не спиннер, а экран «Задача не найдена» с кнопкой «Повторить анализ», которая
переотправляет ту же геометрию. Геометрию и параметры держать в состоянии до
получения результата именно ради этого.

### `POST /predict` — синхронно, Earth Engine не трогает
```jsonc
{"rows":[{"anon_polygon_id":"AOI-0005","date":"2010-04-01",
          "primary_ndvi":null,"landsat_ndvi":0.31,
          "era5_temp_c":8.6,"era5_precip_mm":0.05,
          "crop_type":"озимая пшеница"}],
 "with_anomalies":true}
```
Обязательны только `anon_polygon_id` и `date`. Ответ — то же, что `result` у
`/analyze`, без `fetch` и `area_ha`. Замер: 3195 строк → 0.8 с, ответ 1.4 МБ.

## 6. Аномалия — единый формат в обоих источниках

`data/anomalies.json` (782 штуки) и `result.anomalies` — **одна и та же схема**:

```jsonc
{"anon_polygon_id":"AOI-0005","year":2015,
 "start":"2015-04-01","end":"2015-04-14","days":14,
 "z_min":-4.45,          // глубина просадки в сигмах (самая глубокая точка)
 "z_mean":-2.90,
 "ndvi_mean":0.085,      // средний NDVI за период
 "clim_mean":0.375,      // норма за тот же период
 "drop_vs_norm":-0.290,  // та же глубина, но в единицах NDVI
 "severity":"Критическая аномалия",
 "crop_type":"озимая пшеница",
 "precip_30d":12.4,"precip_30d_norm":38.1,"temp_anom":1.2,
 "precip_ratio":0.33,    // осадки / норма
 "cause":"дефицит осадков",
 "comment":"человекочитаемое пояснение — показывай его как есть"}
```

`severity` — ровно два значения:
`"Угнетение биомассы"`, `"Критическая аномалия"`.

`cause` — ровно пять значений:
1. `дефицит осадков`
2. `температурный стресс`
3. `засуха: осадки ниже нормы и жара`
4. `устойчивое угнетение без явного погодного сигнала`
5. `краткое отклонение, погодой не объясняется (вероятно агрооперация или ошибка данных)`

`status` / `status_pred` — четыре значения:
`"Штатное развитие"`, `"Угнетение биомассы"`, `"Критическая аномалия"`,
`"нет данных"`.

**Списки бери из `data/meta.json` (`crop_types`, `status_values`,
`severity_values`, `causes`), а не из этого документа.** Здесь они приведены
только чтобы ты понимал, какие бывают состояния UI. Для каждого значения
`cause` нужна иконка/цвет — маппинг делай по ключу со `default`-веткой, чтобы
новое значение не уронило экран.

## 7. Статические данные `data/` — форма и подводные камни

| файл | размер | что внутри |
|---|---|---|
| `meta.json` | ~20 КБ | 78 полигонов + словари значений + `totals` |
| `series/<id>.json` | 200–360 КБ | ряд одного полигона |
| `anomalies.json` | ~700 КБ | все 782 аномалии всех полигонов |
| `metrics.json` | ~5 КБ | метрики модели и разрезы |

### `meta.json`
```jsonc
{"polygons":[{"id":"AOI-0001","crop_type":"озимая пшеница",
              "years":[2010,2025],     // ← ЭТО [min, max], А НЕ СПИСОК
              "n_days":3408,"n_observed":615,"n_reconstructed":2793,
              "n_control_points":129,"n_anomalies":15}, …],
 "crop_types":["зерновые","озимая пшеница","пастбища/зерновые","подсолнечник"],
 "totals":{"polygons":78,"days":157140,"observed":48161,
           "reconstructed":108979,"anomalies":782},
 "status_values":[…],"severity_values":[…],"causes":[…]}
```

**Геометрии у полигонов нет.** Ни координат, ни центроида — только id и
счётчики. Поэтому демо-режим строится **без карты** (§8). Не выдумывай
координаты и не расставляй маркеры «примерно»: показывать вымышленные
координаты реальных полей нельзя.

### `series/<id>.json` — параллельные массивы
```jsonc
{"id":"AOI-0001","crop_type":"озимая пшеница",
 "years":[2010,2011,…,2025],   // ← ЗДЕСЬ полный список, в отличие от meta.json
 "date":["2010-04-01","2010-04-02",…],   // длина N
 "ndvi_obs":[null,0.31,null,…],          // null = облако
 "ndvi_filled":[0.378,0.391,…],          // без пропусков
 "ndvi_smooth":[0.377,0.390,…],
 "clim_mean":[0.432,0.435,…],
 "clim_std":[0.177,0.176,…],
 "z":[-0.31,-0.28,…],
 "status":["Штатное развитие",…],
 "is_control_point":[false,…],           // точка, которую оценивало жюри
 "precip_30d":[31.21,…],
 "temp_30d":[9.91,…]}
```
Все массивы одной длины, индекс общий. Так сделано намеренно: объектами это
вчетверо жирнее и переключение полигона тормозит. **Не разворачивай их в массив
объектов ради удобства** — рисуй прямо из типизированных массивов.

Три вещи, которых нет в README и на которые ты напорешься:

1. **`years` значит разное в двух файлах.** В `meta.json` это `[min, max]`,
   в `series/<id>.json` — полный список лет. Не переиспользуй один парсер.
2. **23 ряда из 78 — не суточная сетка.** У них строки только на даты съёмок.
   Пример: `AOI-0008` — 784 строки, `n_observed` 774, даты идут
   `2010-04-07, 2010-04-16, 2010-04-23…`. У `AOI-0006` вообще 60 строк за один
   2025 год. Значит правило «не соединять через зиму» надо обобщить:
   **разрывать линию везде, где между соседними датами больше суток**, а не
   только на границе октябрь→апрель. Один общий алгоритм сегментации решает оба
   случая сразу.
3. **20 полигонов из 78 полностью в статусе `"нет данных"`** — у них
   `clim_mean`, `clim_std` и `z` равны `null` на всём ряду, и аномалий ноль
   (`n_anomalies: 0` в meta). Это те, у кого меньше 3 сезонов: климатнорма
   leave-one-year-out на них не строится. График должен нарисовать ряд NDVI
   без коридора нормы и показать понятную плашку «климатнорма не построена:
   меньше трёх сезонов», а не пустой экран и не ошибку.

### `metrics.json`
```jsonc
{"truth":{"lightgbm":{"n":3112,"RMSE":0.06421,"MAE":0.04039,"MedAE":0.02566,
                      "R2":0.91293,"bias":0.00108,"sMAPE_%":14.78,"p90_AE":0.09105,
                      "max_AE":0.81177,"within_0.05":74.42,"within_0.10":92.03,
                      "GapScore":10.74},
          "линейная интерполяция":{…,"RMSE":0.09695,"GapScore":0.92}},
 "validation":[…],          // на своей валидации, два метода
 "by_gap_length":[{"gap_bucket":"1-3д","lightgbm":0.04279,"linear":0.06567}, …],
 "anomaly_agreement":[{"method":"lightgbm","status_accuracy_%":91.10,
                       "z_RMSE":0.65179,"аномалия_recall_%":65.84}, …],
 "truth_by_group":[…],      // «новый полигон» / «есть в train»
 "truth_by_phase":[…],      // апр, май, июн, июл, авг, сен-окт
 "truth_by_crop":[…],
 "truth_by_gap":[…]}
```
`GapScore = 30 · max(0, 1 − RMSE/0.10)`, максимум 30 — это оценка жюри.
Ключи внутри разрезов бывают **кириллические** (`"группа"`, `"аномалия_recall_%"`)
и с процентом в имени. Типизируй аккуратно, не ломайся на неожиданном ключе.

## 8. Экраны

Четыре маршрута. Шапка общая: название, переключатель «Анализ / Демо / CSV /
Качество модели», индикатор состояния бэкенда (по `/health` и
`meta.gee_available`).

### 8.1 `/` — Анализ области (главный сценарий)

**Левая панель — форма:**
- Карта Leaflet + тайлы OpenStreetMap, начальный вид — по `region_box` из
  `/meta` (`fitBounds`).
- Прямоугольник `region_box` нарисован полупрозрачной рамкой с подписью
  «Регион обучения модели». За его пределами карту не блокируем, но рисование
  валидируем.
- Инструменты рисования: **прямоугольник** и **полигон**. Одна фигура за раз:
  новая заменяет старую. Есть кнопки «Очистить» и «Загрузить GeoJSON» (файлом).
- Валидация вживую, до отправки, с текстом прямо под картой:
  - площадь считается на лету и показывается («6.2 га»); больше
    `max_area_ha` — блокируем кнопку и говорим «обведи поле, а не район»;
  - любая вершина вне `region_box` — блокируем, подсвечиваем фигуру красным;
  - площадь меньше ~0.5 га — предупреждение (пиксель Sentinel-2 это 10 м,
    на крошечной области усреднять нечего); отправку не блокируем.
- Диапазон лет: двойной слайдер от `years.min` до `years.max`, значение по
  умолчанию `years.default`. **Ширина меньше `years.min_span` (3) невозможна** —
  ручки не дают сойтись ближе, рядом висит объяснение почему.
- Культура: селект из `meta.crop_types`, по умолчанию «неизвестно»,
  с подсказкой «с указанной культурой точность чуть выше».
- Кнопка «Проанализировать» — активна, только когда фигура валидна.
- Если `gee_available: false` — вся форма заменяется плашкой: «Earth Engine не
  настроен на сервере», короткая инструкция и кнопка «Открыть демо-режим».

**После отправки — экран прогресса** (§8.2), затем разбор (§8.3).

### 8.2 Прогресс задачи

Поллинг `GET /analyze/{job_id}` раз в **2500 мс** (TanStack Query,
`refetchInterval`, останов на `done`/`error`). Показывать:

- две именованные стадии из поля `stage` — «тянем спутники и погоду» и
  «считаем признаки и восстанавливаем ряд» — как чек-лист, а не как одну полосу;
- прогресс-бар: комбинируй `progress` от бэкенда с локальным таймером,
  ориентируясь на `expected_seconds`, чтобы полоса не стояла минуту на 10%;
- прошедшее время и оценку остатка;
- **как только пришёл `fetch` — показать его немедленно**: сколько суток,
  сколько наблюдений, покрытие в процентах, разбивку по сенсорам
  (S2 / Landsat / MODIS), процент заполненности погоды. Пользователю это
  интересно, и это доказывает, что работа идёт;
- кнопку «Отменить» — она бросает поллинг и возвращает к форме (бэкенд задачу
  не отменяет, это честно пишем мелким шрифтом);
- обработку `404` — экран «Задача потеряна: сервис перезапускался или истёк час
  хранения» + «Повторить» с сохранённой геометрией;
- обработку `status: "error"` — текст `error` как есть + «Изменить область».

Минута ожидания — долго. Займи её чем-то полезным: короткий текст «что сейчас
происходит», или мини-факт о модели.

### 8.3 Разбор — центральный экран

**График (главный элемент, занимает большую часть экрана):**

Слои снизу вверх:
1. **Коридор климатнормы** `clim_mean ± clim_std` — заливка бледным серо-синим
   (в ECharts: два `line` + `stack` + `areaStyle`, нижняя прозрачная).
2. **Линия климатнормы** `clim_mean` — пунктир, серый.
3. **Восстановленный ряд** `ndvi_filled` — сплошная тонкая линия, основной цвет.
4. **Сглаженный ряд** `ndvi_smooth` — сплошная линия потолще; **именно по нему
   считается `z` и находятся аномалии**, так что подписать это в легенде.
5. **Наблюдения** `ndvi_obs` — `scatter`, точки, **никогда не соединять
   линией**: их две трети пропущено, это облака, а не битые данные.
6. **Подсветка аномальных периодов** — `markArea` по `start`/`end` каждой
   аномалии, цвет по `severity` (жёлтый — «Угнетение биомассы», красный —
   «Критическая аномалия»). Клик по области скроллит к её карточке.
7. (Опционально, вторая ось Y) осадки `precip_30d` и температура `temp_30d`.
   По умолчанию выключены, включаются в легенде.

Обязательные свойства графика:
- **Ось Y жёстко `[-0.2, 1.0]`.** Автомасштаб прыгает между полигонами и делает
  графики несравнимыми. Это то же самое, что `config.clip` у модели.
- **Ось X — время** (`type: 'time'`), с `dataZoom` (слайдер снизу + колесо).
- **Сегментация:** линия разрывается везде, где между соседними датами больше
  суток (см. §7 п.2). Реализация: пройти по массиву дат, начать новый сегмент
  при разрыве. Одна функция для обоих источников данных.
- **Быстрый выбор года** — чипсы над графиком: «Все», 2016, 2017 …; клик
  зумит `dataZoom` на сезон.
- **Тултип** по дате: дата, наблюдение (или «облачно»), восстановленное,
  сглаженное, норма ± σ, z, статус, осадки/норма, температура/норма.
  Все числа — по-русски, NDVI с 3 знаками, z с 2, осадки в мм, температура в °C.
- **Контрольные точки** (`is_control_point`, только для демо-данных) —
  отдельным маркером; это точки, по которым модель оценивало жюри. Переключатель
  «показывать контрольные точки».
- Производительность: `large: true`, `sampling: 'lttb'`, `progressive`,
  `animation: false` на рядах длиннее ~2000 точек.

**Карточки аномалий (под графиком, список):**

Одна карточка = один период. На ней:
- заголовок: даты «5 апреля — 12 июня 2019», длительность «69 дней»;
- бейдж `severity` с цветом;
- глубина просадки: **в понятных единицах в первую очередь** — «NDVI 0.19 при
  норме 0.42, это на 45% ниже нормы», и уже потом «z = −2.52» мелким шрифтом
  с тултипом «на сколько стандартных отклонений ниже климатической нормы»;
- причина `cause` с иконкой и цветом;
- погодный контекст: «осадки 21 мм при норме 38 мм (55% нормы)», «температура
  выше нормы на 0.4 °C» — считается из `precip_30d`, `precip_30d_norm`,
  `precip_ratio`, `temp_anom`;
- `comment` целиком — он уже написан по-русски и по-человечески;
- клик по карточке подсвечивает период на графике и зумит к нему.

Сортировка по умолчанию — по `z_min` (сначала самые глубокие), переключается на
хронологическую. Фильтры: по году, по `severity`, по `cause`.

**Пустое состояние обязательно:** у 20 из 78 демо-полигонов аномалий нет вовсе.
Текст не «ничего не найдено», а «За выбранный период угнетения вегетации не
обнаружено — развитие соответствовало климатической норме». Если аномалий нет,
потому что климатнормы нет (`clim_mean` весь `null`) — текст другой, про
нехватку сезонов.

**Сводка (боковая панель):**
- площадь (`area_ha`), культура, годы;
- «2130 суток, из них 728 наблюдений (34.2%), 1402 восстановлено» —
  из `summary` и `fetch`;
- разбивка по сенсорам столбиками: S2 396, Landsat 335, MODIS 130;
- число аномальных периодов и худший `z` (`worst_z`, бывает `null`);
- заполненность погоды `weather_filled_%`;
- сноска: «Анализ одного поля: часть признаков модели опирается на соседние
  поля и здесь недоступна — точность чуть ниже эталонной 0.064 RMSE».

### 8.4 `/demo` — 78 готовых полигонов, без бэкенда

Нужен потому, что Earth Engine может быть не настроен, а показывать продукт надо
всегда. Работает **целиком на статике из `data/`**, ни одного запроса к API.

- **Таблица/список полигонов** (карты нет — координат в данных нет, см. §7):
  колонки `id`, культура, годы (`[min,max]` → «2010–2025»), число суток,
  наблюдений, покрытие в % (считается: `n_observed / n_days`), число аномалий.
  Сортировка по любой колонке, фильтр по культуре и по «есть аномалии».
  Строки с `n_anomalies: 0` помечены спокойным серым бейджем «без аномалий», а
  полигоны с одним сезоном — бейджем «климатнорма не построена».
- Клик по строке грузит `data/series/<id>.json` и рисует **тот же самый экран
  разбора**, что и в §8.3, с аномалиями, отфильтрованными из
  `data/anomalies.json` по `anon_polygon_id`.
- Вверху — плитки из `meta.totals`: 78 полигонов, 157 140 суток, 48 161
  наблюдение, 108 979 восстановлено, 782 аномалии.
- **Режим сравнения:** можно выбрать **второй** полигон и наложить его
  `ndvi_smooth` и коридор нормы на тот же график, вторым цветом, с легендой по
  id и культуре. Строго **не более двух одновременно** — см. граблю про вес
  данных в §13. Сравнение доступно **только в демо-режиме** (там ряды уже
  лежат готовыми файлами); результат `/analyze` в сравнение не подмешивается.
- `anomalies.json` (700 КБ) грузить один раз лениво при входе в демо и держать
  в памяти сгруппированным по `anon_polygon_id`.

### 8.5 `/metrics` — качество модели

README относит этот экран к демо-режиму; делаем отдельной вкладкой, данные —
`data/metrics.json`, тоже без бэкенда.

- Крупно: **RMSE 0.064 против 0.097 у линейной интерполяции**, R² 0.913,
  74.4% в пределах ±0.05, GapScore 10.74 из 30. Рядом — что это значит
  человеческим языком.
- Таблица `truth`: обе модели по всем метрикам, лучший результат в строке
  подсвечен.
- Столбчатые сравнения по разрезам: `by_gap_length` (чем длиннее пропуск, тем
  выше ошибка), `truth_by_phase` (май — самый трудный месяц, август — самый
  лёгкий), `truth_by_crop`, `truth_by_group` (новый полигон против виденного в
  обучении).
- `anomaly_agreement`: точность статуса 91.1% против 85.3%, recall аномалий
  65.8% против 49.9%.
- Каждый разрез снабжён одной строкой вывода на русском, а не голой таблицей.

### 8.6 `/predict` — CSV → готовые строки

- Дроп-зона для CSV, парсинг **PapaParse в воркере** (`worker: true`), файлы
  бывают на тысячи строк.
- Предпросмотр первых 20 строк + определённые колонки.
- Маппинг колонок: обязательные `anon_polygon_id` и `date` — если имена в файле
  другие, дать выбрать их селектами. Остальные колонки уходят как есть
  (`primary_ndvi`, `landsat_ndvi`, `era5_temp_c`, `era5_precip_mm`, `crop_type`
  и любые из схемы исходных данных — чем больше, тем лучше).
- Валидация до отправки: непустой набор строк, обе обязательные колонки на
  месте, даты парсятся, и **предупреждения** (не блокирующие):
  - «в файле только даты съёмок, а не суточная сетка» — признаки и погодные
    накопления считаются по сетке, качество упадёт;
  - «в файле меньше 3 сезонов» — климатнорма пуста, аномалий не будет **молча**;
  - «в файле один полигон» — часть признаков смотрит на соседние поля.
- Отправка `POST /predict` с `with_anomalies: true`, показ того же экрана
  разбора. Ответ до 1.4 МБ — обычный `fetch`, но покажи спиннер с текстом:
  первый запрос после старта бэкенда дольше на пару секунд, грузится модель.
- Ошибки: 400 (пустой `rows` / нет колонки) — текст из `detail`; 422 — «файл не
  соответствует схеме», разверни `detail[]` FastAPI в список понятных строк;
  500 — «ошибка инференса», показать `detail`.

### 8.7 Экспорт

Доступен на любом экране разбора, кнопкой в шапке панели:
- **PNG графика** — `echartsInstance.getDataURL({pixelRatio: 2,
  backgroundColor: '#fff'})`, имя файла `ndvi_<id|USER-AREA>_<годы>.png`.
- **CSV ряда** — колонки `date, ndvi_obs, ndvi_filled, ndvi_smooth, clim_mean,
  clim_std, z, status, precip_30d, temp_30d`; разделитель `;` и BOM `﻿`,
  иначе русский Excel разложит по одной колонке и покалечит кириллицу.
- **CSV аномалий** — все поля из §6.
- **JSON разбора** — то, что пришло от бэкенда, как есть.
Генерация через `Blob` + `URL.createObjectURL`, никаких серверных ручек.

## 9. Адаптер — напиши его первым

Два источника дают **одни и те же данные в двух формах**:

| | демо (`data/series/<id>.json`) | API (`result.series`) |
|---|---|---|
| форма | параллельные массивы | массив объектов |
| статус | `status` | `status_pred` |
| id | поле `id` на корне | `anon_polygon_id` в каждой строке |
| погодные нормы | нет `precip_30d_norm`, `temp_30d_norm`, `temp_anom` | есть |
| контрольные точки | `is_control_point` | нет |
| годы | полный список в `years` | выводится из строк |

Заведи **один внутренний тип** и два конвертера в него:

```ts
// src/adapters/series.ts
export type SeriesView = {
  id: string;
  cropType: string;
  years: number[];
  n: number;
  date: string[];            // всегда массивы: график ест их напрямую
  ndviObs: (number|null)[];
  ndviFilled: (number|null)[];
  ndviSmooth: (number|null)[];
  climMean: (number|null)[];
  climStd: (number|null)[];
  z: (number|null)[];
  status: string[];
  precip30d: (number|null)[];
  temp30d: (number|null)[];
  precip30dNorm?: (number|null)[];   // только из API
  temp30dNorm?: (number|null)[];
  tempAnom?: (number|null)[];
  isControlPoint?: boolean[];        // только из демо
  hasClimateNorm: boolean;           // false, если climMean весь null
};

export function fromStaticSeries(raw: StaticSeries): SeriesView
export function fromApiSeries(rows: ApiSeriesRow[], meta): SeriesView
```

Аномалии совместимы один в один — общий тип без конвертеров.

**Это не факультатив.** Если адаптера нет, у тебя будет два кода отрисовки
графика, они разъедутся, и вторая половина граблей из §13 будет починена только
в одном из них. Пишется в десяток строк, пиши сразу.

Сегментация сезонов тоже живёт здесь:
```ts
export function segments(date: string[]): Array<[number, number]>
// разбивает индексы на непрерывные куски: разрыв там, где между соседними
// датами больше 1 суток. Покрывает и зиму, и разреженные ряды из §7 п.2.
```

## 10. Тексты и локализация

- Интерфейс **полностью русский**. Английских подписей быть не должно.
- **Все доменные значения приходят из данных** — культуры, статусы, severity,
  причины, комментарии к аномалиям. Не хардкодить списки: бери из
  `data/meta.json` и `GET /meta`. Маппинг «значение → цвет/иконка» обязан иметь
  ветку по умолчанию.
- Числа: разделитель тысяч — пробел (`157 140`), десятичный — запятая
  (`0,064`). Используй `Intl.NumberFormat('ru-RU')`.
- Даты: `Intl.DateTimeFormat('ru-RU')`, «5 апреля 2019».
- Термины переводить, а не показывать: `z-score` → «отклонение от нормы в
  стандартных отклонениях» (с тултипом), `coverage` → «покрытие наблюдениями»,
  `reconstructed` → «восстановлено», `RMSE` → оставить, но объяснить рядом.

## 11. Ошибки и пустые состояния — полный перечень

Каждое должно быть реализовано и проверено вручную:

| ситуация | что показать |
|---|---|
| `/health` не отвечает | «Бэкенд недоступен по `VITE_API_URL`» + команда запуска + «Открыть демо-режим» |
| `gee_available: false` | плашка вместо формы + инструкция + кнопка в демо |
| фигура вне `region_box` | подсветка фигуры, блокировка кнопки, текст с координатами |
| площадь > `max_area_ha` | «6 200 га больше предела 5 000 га: обведи поле, а не район» |
| выбрано < 3 сезонов | слайдер не даёт, плюс объяснение про leave-one-year-out |
| 400 от `/analyze` | текст `detail` как есть, форма остаётся заполненной |
| 503 от `/analyze` | инструкция по Earth Engine + кнопка в демо |
| 404 при поллинге | «Задача потеряна» + «Повторить» с той же геометрией |
| `status: "error"` | текст `error` + «Изменить область» |
| аномалий 0 | «Угнетения вегетации не обнаружено…» |
| климатнормы нет (весь `clim_mean` null) | график без коридора + плашка про 3 сезона |
| `worst_z: null` | прочерк, не `NaN` и не `null` на экране |
| `status: "нет данных"` в начале ряда | на графике зона без коридора, в тултипе «климатнорма ещё не построена» |
| CSV без обязательной колонки | список недостающих колонок + селекты маппинга |
| очень медленная сеть | скелетоны, а не пустой белый экран |

Сетевой слой: таймаут 15 с на быстрые ручки, поллинг без таймаута, но с
предельным числом попыток (`expected_seconds × 3 / 2.5`), потом — «слишком
долго, попробуйте позже».

## 12. Качество кода — это продуктовый MVP, не хакатонная поделка

- TypeScript **strict**, `noUncheckedIndexedAccess`. `any` не проходит ревью.
- Типы ответов API — **сгенерированные** из `openapi.json`, шаг генерации в
  `package.json` (`pnpm gen:api`).
- Никаких обращений к `fetch` из компонентов: весь HTTP — в `src/api/`,
  весь доступ к статике — в `src/data/`.
- Компоненты в `components/` не знают о доменных типах API; они принимают
  готовые пропсы.
- **Тесты (Vitest), обязательные:**
  1. `segments()` — зима, разреженный ряд `AOI-0008`, односезонный `AOI-0006`,
     пустой массив;
  2. `fromStaticSeries` / `fromApiSeries` — на реальных файлах
     `data/series/AOI-0001.json` и `samples/analyze_response.json`; проверить,
     что оба дают одинаковую форму `SeriesView`;
  3. валидация геометрии — площадь, попадание в `region_box`, минимум сезонов;
  4. форматтеры чисел и дат;
  5. группировка аномалий по `anon_polygon_id`;
  6. поллинг: `queued → running → done`, ветка `404`, ветка `error` (мокнутый
     клиент, без сети).
- Доступность: у карты есть текстовая альтернатива ввода координат, у графика —
  таблица данных за выбранный сезон по кнопке, фокус видимый, контраст AA,
  цвет **не единственный** носитель смысла (severity — цвет + иконка + текст).
- Производительность: демо-полигон переключается меньше чем за 300 мс после
  загрузки файла; в состоянии **не больше одного-двух разборов** одновременно
  (см. §13).

## 13. Грабли — требования, а не советы

1. **Не соединять линию через зиму.** В данных только 1 апреля — 30 октября.
   Между 30 октября и 1 апреля разрыв; сплошная линия протянет через зиму
   прямую, которой не существует.
2. **Разрывать линию на любом пропуске больше суток**, не только на границе
   сезона: 23 ряда из 78 содержат только даты съёмок (§7 п.2).
3. **Ось Y жёстко `[-0.2, 1.0]`.** Автомасштаб делает полигоны несравнимыми.
4. **`ndvi_obs` разрежен на две трети** — это облака, а не битые данные.
   Только точками, пропуски не соединять.
5. **Минимум 3 сезона.** Климатнорма строится leave-one-year-out; на одном
   сезоне она пуста, ряд восстановится, а аномалий не найдётся **молча**.
   Бэкенд отклоняет меньшее, но и UI не должен давать выбрать.
6. **`z` считается от `ndvi_smooth`, не от `ndvi_filled`.** Сглаженный ряд не
   даёт ложных срабатываний на одиночных выбросах. Если сам что-то пересчитываешь —
   бери `ndvi_smooth`.
7. **`status: "нет данных"`** бывает в начале ряда: климатнормы там ещё нет.
   Это нормальное состояние, не ошибка.
8. **Все тексты русские и приходят из данных.** Не хардкодь списки культур,
   статусов и причин.
9. **20 полигонов из 78 без аномалий** — пустое состояние обязательно.
10. **Ответ жирный:** 0.9 МБ на поле за 10 лет, ~1.5 МБ за 16. Не держи в
    состоянии несколько разборов сразу; исключение — режим сравнения в демо,
    и там строго два.
11. **Задачи живут в памяти процесса бэкенда.** Рестарт — и `job_id` протух,
    `GET /analyze/{id}` вернёт 404. Результат хранится час. Обработай: предложи
    повторить, не показывай вечный спиннер.
12. **Одно поле за раз.** Модель обучалась там, где часть признаков смотрит на
    соседние поля в ту же дату; для одиночной области они пусты, и точность чуть
    ниже эталонной. Это ожидаемо, а не поломка — так и напиши в сводке.
13. **`years` в `meta.json` — это `[min, max]`, в `series/*.json` — полный
    список.** Разные парсеры.
14. **Не выдумывай координаты демо-полигонов.** Их нет в данных, и показывать
    вымышленные координаты реальных полей нельзя.
15. **CSV-экспорт — с BOM и `;`**, иначе русский Excel испортит и кодировку, и
    разбиение на колонки.

## Приложение: справочные значения

Не хардкодить — только чтобы понимать, какие бывают состояния.

**Культуры** (`meta.crop_types`): зерновые, озимая пшеница, пастбища/зерновые,
подсолнечник; в `GET /meta` есть ещё «неизвестно».

**Статусы**: Штатное развитие · Угнетение биомассы · Критическая аномалия ·
нет данных.

**Severity**: Угнетение биомассы · Критическая аномалия.

**Причины**: дефицит осадков · температурный стресс · засуха: осадки ниже нормы
и жара · устойчивое угнетение без явного погодного сигнала · краткое отклонение,
погодой не объясняется (вероятно агрооперация или ошибка данных).

48 161 наблюдение, 108 979 восстановлено, 782 аномалии.

**Сезон**: 1 апреля — 30 октября, 213 суток в году.

**Замер живого вызова** (`samples/`): поле 6.2 га, 10 сезонов → выгрузка 57 с,
модель 0.6 с, 2130 суток, 728 наблюдений (34.2%), 7 аномальных периодов,
ответ 0.9 МБ.
